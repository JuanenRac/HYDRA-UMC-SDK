# Contract source: the SDK as the origin of the server contract

This document describes how the contract of the HTTP routes of HYDRA-UMC-SERVER
moves, step by step, from "written in the server and copied into the SDK" to
"written in the SDK and checked against by the server". It also describes the
first step already taken (the pilot) and how to add to it.

## Where the contract is born today

| Artifact | Born in | Reaches the SDK how |
| --- | --- | --- |
| Inventory of every route (`docs/openapi.json` of the server) | generated by the server from the `app.<method>(...)` calls of its sources, plus the typed bodies written by hand in `tools/openapi_types.mjs` | copied by hand into `contracts/openapi/v1/server.full.openapi.json` at each SDK version |
| Typed slice promised to clients (`server.openapi.json`) | written by hand in the SDK | already owned by the SDK; the server checks that it offers every route of it (`tools/verify_sdk_contract.mjs`) |
| Closed message schemas (`contracts/json-schema/v1/*.schema.json`) | written in the SDK | vendored into the Go, Rust and TypeScript clients with a hash manifest; the Python client implements them in code and a differential test compares both |
| Shapes inside the server (`tools/openapi_types.mjs`, the enums in `src/connections.ts`) | the server, by hand | **nothing compares them with the SDK schemas** |

So two things already point the right way (the typed slice and the closed
schemas are owned by the SDK) and two do not: the full inventory flows from
the server to the SDK, and the server keeps its own hand-written copy of the
shapes. The consequences are the ones to expect: a route added to the server
is unknown to the SDK until the next version copies it (the Studio and the
Suite keep an exemption list of routes "not yet in the contract" for exactly
that reason), and a field changed on one side can survive for a long time on
the other.

## The goal

The SDK is the **source**; the server **generates and validates against it**.

* The shape of a route (method, path, access, query parameters, status codes,
  the schema of every answer) is declared once, in a small source file of the
  SDK, next to the closed schema it uses.
* The OpenAPI document of that group is **generated** from the source; nobody
  edits it.
* The server does not decide the contract any more: its build fails when the
  inventory it generates from its own code differs from the SDK source (a
  route missing, another access, a status code the handler does not produce,
  a query parameter read or not declared, a schema with other fields).
* The clients (Studio, Suite, the phone apps, the SDK clients) are checked
  against the same source: they may only call routes, and send query
  parameters, that the source declares.

Direction of the flow after the change:

```
SDK source (contracts/sources) ──generate──> OpenAPI of the group (SDK)
        │                                              │
        ├──check──> server inventory + server enums    └──> clients vendored from it
        └──check──> consumers (routes and parameters they use)
```

## Principles

1. **One step per group of routes.** The inversion is made group by group
   (connections first), never in one block. A group that is not in the source
   keeps working exactly as today.
2. **Only additive changes in a published line.** A generated document is a new
   file; the existing `server.openapi.json` and `server.full.openapi.json` do
   not change shape. Fields are never renamed or removed inside a major
   version (see Compatibility in [CONTRACTS.md](CONTRACTS.md)).
3. **The check is cheap and local.** It needs only the sibling checkouts; with
   none of them it reports a skip, and it fails instead when
   `HYDRA_UMC_REQUIRE_WORKSPACE=1` is set (the setting meant for a release
   check run with every checkout present).
4. **The closed schemas stay the normative source** for the shape of a
   message. The route source references them; it never duplicates their
   fields.
5. **Characterization first.** Before a group moves, tests pin what the server
   offers today. The source is then written to equal it; any difference found
   on the way is a real finding fixed on the side that is wrong.

## Phases

| Phase | Content | Done when |
| --- | --- | --- |
| 0. Pilot | One group (the connection routes): source file, generator, `--check`, characterization tests, and the same check in the server build | `python tools/contract_source.py --check` passes and fails on every kind of drift the tests inject |
| 1. Typed slice | Move the routes of `server.openapi.json` (discovery, login, settings, commands, claims, safety limits) into sources, one group per file, generating the document that is hand-written today | the generated document equals the published one byte for byte, then replaces it |
| 2. Remaining inventory | Add the routes that only exist in `server.full.openapi.json` group by group (the order follows how much clients depend on the group); the full document becomes the union of the generated ones | `server.full.openapi.json` is generated, not copied |
| 3. Server types from the SDK | The server's `tools/openapi_types.mjs` stops carrying shapes of its own: the answer schemas are read from the SDK checkout (or from a vendored, hash-checked copy) when the inventory is built | removing a schema from the SDK breaks the server build, not the other way round |
| 4. Clients | Generate or check the route tables of the clients (Studio, Suite, phone apps) from the source; drop the "not yet in the contract" exemptions | no client keeps a hand-written list of known routes |

Each phase ends with its own version of the SDK and, where the server or a
client changes, of that repository.

## How drift is detected

`tools/contract_source.py --check` is the single entry point. For every source
under `contracts/sources` it verifies:

* **the generated document** is exactly what the source produces;
* **the schema copies**: every vendored copy of the closed schemas is
  byte-identical to `contracts/json-schema/v1` and listed in its
  `manifest.json` with the right hash;
* **the server**: its inventory offers every declared route with the same
  method and access, produces every declared status code (the codes a shared
  middleware adds, 401, 403 and 429, are not asked of the handler) and no
  undeclared one, reads exactly the declared query parameters, and carries the
  closed schemas with the same required fields, closed/open flag, enums,
  patterns and formats; the enums in the server sources equal the schema enums;
* **the consumers**: every route under a source path that a client mentions
  exists in the source, and every query parameter it sends to it is declared.

The same server-side comparison runs in the server's own build
(`tools/verify_sdk_contract.mjs`), so the drift is caught on whichever side
changes first. The checks never write anything and never contact a service.

Where it runs:

* in the SDK's CI and local build test, for the generated document, the schema
  copies and the characterization tests; the sibling checkouts are skipped
  there because the CI checks out only the SDK;
* in the server's `npm test`, whenever an SDK checkout is found next to it or
  through `HYDRA_UMC_SDK_DIR`; the server's CI pins the SDK to a tag, so it
  sees a new generated document once it repins to the tag that carries it
  (pointing `HYDRA_UMC_SDK_DIR` at that checkout is what makes the check run
  there, and `HYDRA_UMC_REQUIRE_SDK=1` makes a missing checkout a failure);
* by hand before a release, with the sibling checkouts present and
  `HYDRA_UMC_REQUIRE_WORKSPACE=1`, which turns every skip into a failure.

## Migrating without breaking the repositories pinned to a tag

Repositories pin the SDK to a tag. A tag never changes, so everything below is
about what the next tag adds and the order of the steps:

1. **SDK first.** The source, the generated document and the tool are added in
   the SDK. They are new files; a consumer that does not know them is not
   affected. The SDK is published with a new tag.
2. **Server second.** The server accepts the new document when it finds it and
   keeps working when the SDK checkout it meets is older (the document is
   optional in its check). Its release follows the SDK tag.
3. **Clients last.** After the new tag exists, each client repins to it and
   removes its own exemption (for the connection routes, the "not yet in the
   contract" entry of the Studio and the Suite). A client that has not repinned
   keeps passing with its old pin.
4. **No in-place change of a published file.** `server.full.openapi.json` is
   refreshed only at an SDK version, as today. A generated document replaces a
   hand-written one only in the phase where both are proven byte-identical.
5. **Rollback is deleting a source.** Removing a source file and its generated
   document returns the group to the previous situation without touching any
   other group; no consumer reads the source itself, only the generated
   document.

## Risks and how they are covered

| Risk | Cover |
| --- | --- |
| The source and the real behavior disagree from the start | the characterization tests pin the routes first; the pilot found one such case (the server's copy of a schema lacked the `app_version` pattern the handler really enforces) and the server side was corrected |
| The check is skipped for ever because no checkout is near | `HYDRA_UMC_REQUIRE_WORKSPACE=1` for a release check; the skip is printed, not silent |
| A consumer scan produces false alarms on strings that only look like routes | the scan only looks at paths under a declared prefix, ignores test folders and build output, and reports the file |
| The server inventory is built by reading its sources with patterns, so it can miss a parameter | the check compares against what the inventory reports and the inventory has its own `--check`; a handler that reads a parameter in a way the patterns miss is a gap to close in the inventory, not in the source |
| A phase touches every consumer at once | one group per step, additive documents, repin at the consumer's own pace |
| Two sources claim the same path | the generator refuses it (one path, one method, one source) |
| Handwritten and generated documents drift apart during phase 1 | the phase finishes only when they are byte-identical; until then the hand-written one stays authoritative |

## The pilot: the connection routes

* Source: [`contracts/sources/connections.routes.json`](../contracts/sources/connections.routes.json)
  declares `GET /api/connections/clients` and `GET /api/connections/events`
  (signed-in access, status 200 and 400, the query parameters with their enums
  and patterns) and refers to the closed `ConnectionClient` and
  `ConnectionEvent` schemas.
* Generated: `contracts/openapi/v1/server.connections.openapi.json`
  (`python tools/contract_source.py` rewrites it).
* Check: `python tools/contract_source.py --check` (options `--server`,
  `--consumer`, `--workspace`).
* Tests: `clients/python/tests/test_contract_source.py` pins the routes and
  shapes the server offers and injects each kind of drift to prove the check
  fails on it.
* Server side: `tools/verify_sdk_contract.mjs` reads the generated documents
  too, so the server build fails when its routes, access, status codes, query
  parameters or the two closed schemas differ from the SDK.

What the pilot deliberately does not do: it does not touch any other group,
does not change `server.openapi.json` or `server.full.openapi.json`, and does
not make the server read its schemas from the SDK (phase 3). Until the SDK
carries a tag with the pilot, the Studio and the Suite keep their exemption for
these two routes.

### Adding a route to a group

1. Add it to the source (`method`, `path`, `operationId`, `access`, `query`,
   `responses`).
2. Run `python tools/contract_source.py` and commit the regenerated document.
3. Make the server register the route; its inventory (`npm run openapi`) must
   then show the same method, access, status codes and query parameters.
4. Run `python tools/contract_source.py --check` and the server's `npm test`.
5. If a closed schema changes, change it in `contracts/json-schema/v1`, copy it
   into the vendored directories and regenerate the manifests as for any
   schema change.

## What the clients do after they repin

The routes below are in `server.full.openapi.json` from the SDK version that carries them, so a client that pins that
version no longer needs to exempt them:

* **HYDRA-UMC-STUDIO:** in `tests/restPaths.test.ts` the list `notYetInContract` (`/api/connections/clients`,
  `/api/connections/events`, `/api/ecosystem/health`) is emptied and the filter that uses it is removed, so every route
  the Studio calls must exist in the contract.
* **HYDRA-UMC-SUITE:** in `tests/test_rest_routes.py` the set `NOT_YET_IN_CONTRACT` (the same three routes) is emptied
  and the condition that uses it is removed.
* Both change in the same commit as the repin (`python tools/pin_sdk.py`), because with the old pin the contract next to
  them does not list the routes and the test would fail. A client that has not repinned keeps passing with its old pin.
* A client that also wants the liveness of the robots, the heartbeat or the release of the global stop calls
  `/api/robots/liveness`, `/api/robot/{id}/heartbeat` and `/api/stop-all/release`: they are in the same document, and the
  answers are the `RobotLiveness` contract, `{success}` and `{success, announced}`.
