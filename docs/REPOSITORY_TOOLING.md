# Repository tooling

Every repository of the family carries a few files that must be the same everywhere.
They are kept identical from this SDK, not copied by hand.

| File | Rule |
|---|---|
| `bump_manifest_version.py` | One canonical copy in `tools/canonical/`. Only repositories that already have it get it (the bridges keep their own bump script). |
| `tools/hydra_project_tool.py` | One canonical copy in `tools/canonical/`, in every repository. |
| `.github/workflows/dashboard-dispatch.yml` | One canonical copy in `tools/canonical/`, in every repository. |
| `tools/_doc_policy.py` | Generated by `sync_doc_policy.py` from `clients/python/src/hydra_umc_sdk/doc_policy.py`. |
| `tools/_readme_parity.py` | Generated by `sync_readme_parity.py`. Checks that the eight READMEs have the same sections and links, and that the file tree of each one lists every first-level entry that Git versions (build scripts, licences, lock files and the like are not asked for). |
| `tools/ci_validate.py`, `tools/build_test.py` | One canonical copy in `tools/canonical/` each. A repository adopts it when its copy holds nothing of its own; what a repository has of its own goes in `tools/extra_checks.py` and `tools/extra_build_steps.py` (see below). |
| `.github/workflows/ci.yml` | Differs by technology (Node, Python, Rust, Go, Flutter, Gradle, firmware): which jobs exist depends on the stack. Grouped into families and listed by `sync_repo_tools.py`; not rewritten. |

## Changing a shared file

1. Edit the canonical copy in `tools/canonical/` (never a copy inside another repository).
2. Run `python tools/sync_repo_tools.py` from this repository with the other repositories checked out next to it.
3. In each repository that changed, run `python tools/hydra_project_tool.py validate`, commit and push once.
4. `python tools/sync_repo_tools.py --check` must end with `CANONICAL_TOOLS=PASS`. The nightly family check of HYDRA-UMC-DOCS runs the same command.

## The project tool

```
python tools/hydra_project_tool.py validate   # tools/ci_validate.py with HYDRA_UMC_CI=1
python tools/hydra_project_tool.py test       # tools/build_test.py with HYDRA_UMC_CI=1
python tools/hydra_project_tool.py ci         # validate, then test
python tools/hydra_project_tool.py version    # the declared version and the next one
python tools/hydra_project_tool.py status     # clean tree? manifest not older than the last tag?
python tools/hydra_project_tool.py bump       # the only command that changes the version
python tools/hydra_project_tool.py doctor     # read-only: what is wrong here, and what to do about it
python tools/hydra_project_tool.py coverage   # tests under a coverage tool, compared with a floor (a warning)
```

`validate`, `test` and `ci` fail if the manifest version changed while they ran. `bump --dry-run` prints the
version it would produce and writes nothing; `bump` refuses a dirty working tree unless `--allow-dirty` is given.

The version written to a native file is the form its toolchain accepts: Cargo (`Cargo.toml` and the package entry of `Cargo.lock`) takes `a.b.c` or `a.b.c+d`, and a Flutter `pubspec.yaml` takes `a.b.c+N`, where `N` is a build number raised by one on every bump (the generated `lib/app_version.dart` follows it), and npm (`package.json` and `package-lock.json`) takes `a.b.c`, so the fourth component is not stored there (a `package.json` that still holds all four is accepted until the next bump rewrites it). `bump` and `doctor` report a value the toolchain would reject instead of writing it.
The version always follows the odometer rule: three components up to 0.7.9, four from 0.8.0.0.

## The doctor

`python tools/hydra_project_tool.py doctor` checks one repository against the shared rules and writes nothing. It prints one
line per problem with the fix under it, and ends with `DOCTOR=PASS` or `DOCTOR=FAIL <n>` (exit 1):

```
OK    manifest
FIX   shared tools: tools/hydra_project_tool.py differs from the shared copy
        -> python tools/sync_repo_tools.py in HYDRA-UMC-SDK, then commit here
SKIP  glance: no HYDRA-UMC-DOCS checkout next to this repository (set HYDRA_UMC_DOCS_DIR)
DOCTOR=FAIL 1
```

| Check | What it looks at |
|---|---|
| `manifest` | The required keys, the ecosystem, the name against the directory, the version, and the values of `role`, `deployment_target` and `maturity` |
| `readme` | The universal layout (`tools/universal_readme_check.py`): the eight files, the sections, their order and the status table |
| `glance` | The At a glance section, through `make_glance.py --check` of HYDRA-UMC-DOCS (skipped without that checkout) |
| `changelog` | A heading for the manifest version with a note under it |
| `shared tools` | The files of `tools/canonical/` and the per-repository copies, through `drift_of_repository()` of `sync_repo_tools.py` in the SDK checkout (skipped without it) |
| `sdk pin` | Every reference to the SDK in `pyproject.toml`, the requirements files and `ci.yml` is a release tag, and the newest one of the SDK checkout |

A sibling checkout is looked for next to the repository, or in `HYDRA_UMC_DOCS_DIR` and `HYDRA_UMC_SDK_DIR`. The doctor adds no
rule of its own: each check is one the CI validator or `sync_repo_tools.py --check` already runs, gathered in one list.

## The coverage floor

`python tools/hydra_project_tool.py coverage` runs the tests of a repository under the coverage tool of the stack and compares the
result with `tools/coverage_floor.json`, a list with one entry per stack:

| Key | Meaning |
|---|---|
| `stack` | `python` (needs `coverage` and `pytest`), `go` or `node` (`--experimental-test-coverage`) |
| `floor` | The percentage below which the command warns |
| `workdir` | Where the tests run, relative to the repository (default `.`) |
| `source`, `tests`, `pythonpath` | Python: the package measured, the test folder and the folder to put on `PYTHONPATH` |
| `tests` | Node: the list of test files |

Below the floor it prints `WARN` and still exits 0; `--strict` makes it exit 1. A repository without the file prints
`COVERAGE=SKIP`; a tool that is not installed prints `SKIP` for that entry. The command is not part of `validate`, `test` or `ci`,
and the CI does not run it. Rust has no entry because no coverage tool is installed on the workstation. Floors set so far, a few points
under what was measured: Python client 90 (measured 94, with branches), Go client 75 (81), TypeScript client 90 (95).

## Pinning the SDK

A repository that depends on this SDK names a release tag, never a branch or a bare commit:

```
hydra-umc-sdk @ git+https://github.com/JuanenRac/HYDRA-UMC-SDK.git@v0.3.6#subdirectory=clients/python
```

After publishing a new SDK release, run `python tools/pin_sdk.py` to move every consumer to it and
`python tools/pin_sdk.py --check` to list the ones that are behind.

## The validator, the secret redaction and the port registry

* `tools/canonical/ci_validate.py` is the shared validator. A repository adopts it when its own copy holds nothing of its own (ignoring comments, blank lines and `import subprocess`, every line it has is also in the canonical one); `sync_repo_tools.py --check` fails for a copy that lacks a shared check, and the repositories that add checks of their own (the bridges, the URDF editor, STUDIO) are listed as adaptations instead.
* `tools/canonical/build_test.py` is the shared build test, with the same adoption rule. After the build of the stack it runs `tools/extra_build_steps.py` when the repository has one (its own tests, verifiers or a second toolchain), from the repository root with the same environment; a non-zero exit fails the build test.
* `tools/extra_checks.py` holds the checks a repository has besides the shared validator. It defines `check(root) -> list[str]`, one sentence per problem, and the canonical validator runs it as its last step. Only a repository with checks of its own has one (STUDIO checks its Work catalogue there).
* `tools/canonical/previous/` keeps the text a canonical file had before its latest change: a copy that holds nothing but those older lines is a stale copy (rewritten by `sync_repo_tools.py`), not an adaptation. Drop the file once every repository has the new text.
* `contracts/ports.yaml` is also copied byte for byte to `HYDRA-UMC-OS/provisioning/ports.yaml` (`PER_REPOSITORY_FILES`), where the installers and `verify_cm5_runtime.sh --with-services` read the port, the health route and the unit of each service. After `sync_ports.py` changes the registry, run `sync_repo_tools.py` so the copy follows.
* `tools/canonical/redaction.py` is the one secret redaction for Python. It is vendored byte for byte into the ops agent and the local technician (`PER_REPOSITORY_FILES` in `sync_repo_tools.py` says where), together with `contracts/redaction/vectors.json`, the cases every implementation, in any language, has to pass. A new rule is added in the canonical file and in the vectors, then `sync_repo_tools.py` copies both.
* `contracts/ports.yaml` is the registry of the port, health path and systemd unit of every service, generated by `tools/sync_ports.py` from the `service` block of each manifest and the `--port` of its unit. `sync_ports.py --check` fails when the registry is out of date, when two services share a port, when a manifest and its unit disagree on the port, when a named unit has no file, and when an installer of HYDRA-UMC-OS names a unit that no repository ships.

## Checks of the shared validator

Besides the manifest, the documents, the links and the README layout, `tools/canonical/ci_validate.py` fails for:

* **A hand-written test count in the manifest `notes`** ("142 tests", "tests: 142", "142 passing"). A count written by hand is wrong as soon as a test is added; the README states the count and the documentation tools check it against the code.
* **A CHANGELOG without a note for the manifest version**: the heading of the version must exist and have at least one line of text under it. On a tag build (`GITHUB_REF_TYPE=tag` or a `refs/tags/` reference) the tag must also name the manifest version (`v1.2.3` for `1.2.3`), so a tag cannot be pushed before the version is promoted in the changelog.
* **A stale "At a glance" or "Project status" section**: when the documentation repository is checked out next to the repository (or named in `HYDRA_UMC_DOCS_DIR`) and its `data/glance.json` lists the repository, the validator runs `make_glance.py --check --repo <name>`. A plain CI checkout has no sibling, so there the check is skipped and the nightly run of the documentation repository covers it.
* **The checks of the repository itself**, from `tools/extra_checks.py`, last.

## Designs that are not built yet

* **Offscreen tests of the graphical tools**: run each Qt or Tk window with the offscreen platform, take its widget tree and compare it with a stored list of names. It needs a Qt platform plugin on the CI runner and a policy for what a harmless difference is.
* **Common templates** (issue and pull request templates, the security policy text): one canonical copy in `tools/canonical/` synced like `dashboard-dispatch.yml`. The texts differ today by repository name and contact; they need one agreed wording first.

## The release file of the family

`ecosystem-release.json` is the one answer to "which versions go together": for a release of the family it lists the version and the commit of every repository (`{"schema_version", "ecosystem", "repositories": [{"name", "version", "commit"}]}`, sorted by name). It is written by `tools/ecosystem_release.py` in this repository and published in the documentation repository as `data/ecosystem-release.json`.

```
python tools/ecosystem_release.py --write   # read every manifest and Git head next to this repository; write the file in HYDRA-UMC-DOCS
python tools/ecosystem_release.py --check   # the file is well formed and no repository disagrees with it
python tools/ecosystem_release.py --print   # show what --write would write
```

Run `--write` once for each release of the family and commit the file in the documentation repository. The shared validator (`tools/canonical/ci_validate.py`) checks the entry of the repository it runs in whenever the documentation checkout is next to it (or named in `HYDRA_UMC_DOCS_DIR`): the listed version must not be ahead of the manifest and the listed commit must be in the repository's history (the commit check is skipped in a shallow clone). Without that checkout the check is skipped, as the glance check is.

## Checks without Git

The public/private boundary check of `tools/_doc_policy.py` uses `git grep`. When the checkout is not a Git working tree, or Git is not installed, it reads the text files itself (skipping `node_modules`, build output, caches and binary files) and applies the same three rules, so `ci_validate.py` also runs on a source archive. The check of the first-level entries of the README tree needs Git and is skipped without it.
