# TypeScript reference client

Real, tested TypeScript client for the HYDRA-UMC-SDK v1 contracts documented
in [../../docs/CONTRACTS.md](../../docs/CONTRACTS.md): hand-written types
plus real Ajv-based runtime validation, mirroring the scope of the
[Python reference client](../python) for a second language.

The published JSON Schema files under `contracts/json-schema/v1/` remain
the **normative source**. Unlike the Python client (which hand-reimplements
the required v1 subset in pure Python - see
[../../docs/PYTHON_CLIENT.md](../../docs/PYTHON_CLIENT.md)), this package
compiles and enforces the real schema files directly through
[Ajv](https://ajv.js.org/), so it validates the full schema, not a
reimplemented subset.

## What's here

- **`src/types.ts`** - hand-written TypeScript interfaces for the 7 payload
  contracts (`DeviceDescriptor`, `HealthReport`, `SafetyState`,
  `UpdateManifest`, `EventEnvelope`, `ServerDiscovery`, `ProjectManifest`),
  field-for-field from the schema files. **Not generated by a tool** - no
  `json-schema-to-typescript`/`quicktype` run; these are written directly
  against each `*.schema.json`'s `required`/`properties`, the same way
  `clients/go/types.go` is for Go. `ContractManifestEntry`/
  `ContractManifest` mirror `manifest.json`'s own shape (the generated
  integrity manifest listing every schema file's sha256 - see
  `contracts/generate_manifest.py`); it is data, not itself a JSON Schema,
  so it is not one of the 7 names `validate()` accepts.
- **`src/validation.ts`** - `validate(contract, payload): void` (throws
  `ContractValidationError` on the first violation, mirroring the Python
  client's own function signature and error type) and `isValid(contract,
  payload): boolean`, both backed by
  [`ajv`](https://www.npmjs.com/package/ajv)'s `Ajv2020` class (this
  client's schemas declare `"$schema":
  "https://json-schema.org/draft/2020-12/schema"`) with
  [`ajv-formats`](https://www.npmjs.com/package/ajv-formats) enabled so
  `format: "date-time"` (used by every `timestamp_utc` field) is a real,
  enforced check, not a parsed-and-ignored annotation. Schemas are compiled
  from this package's own vendored copy under `schemas/`, shipped alongside
  `dist/` so a published package needs no access to the monorepo's
  `contracts/` directory at runtime.
- **`src/manifest.ts`** - `verifyContractManifest()`, a bonus real
  integrity check: recomputes the sha256 of every vendored schema file and
  compares it against `schemas/manifest.json`'s own claim for that file.

## Real, found-and-fixed bug

Writing this package's own `verifyContractManifest()` test caught a
genuine, pre-existing drift shared with the Go and Rust clients (all three
vendor the same file): `contracts/json-schema/v1/manifest.json`'s recorded
sha256 for `update-manifest.schema.json` was stale - the schema file
itself was edited after the manifest was last regenerated (matching the
SemVer `pattern` addition documented in the root `CHANGELOG.md`'s `[0.0.5]`
entry), but nobody re-ran `contracts/generate_manifest.py` afterwards.
Fixed by re-running that generator and correcting the one stale digest
directly in `contracts/json-schema/v1/manifest.json`; all 7 entries now
verify against the real file contents on disk.

## Build & test

```bash
cd clients/typescript
npm ci
npm run typecheck   # tsc -p tsconfig.json --noEmit
npm test            # builds src/ and tests/, then node --test dist-tests/*.test.mjs
```

All commands above were run for real against this exact source tree
(Node v20 and v26.6.0, TypeScript 7.0.2, npm 12.0.2) before this client
was committed - `npm ci`, `npm run typecheck`, and `npm test` all pass:
22/22 tests, including:

- One accept + one reject test per contract, loaded straight from
  `conformance/fixtures/v1/*.valid.json` / `*.invalid.json` - the exact
  same fixtures `clients/python/tests/test_validation.py` and
  `clients/go/validation_test.go` use.
- `verifyContractManifest finds no mismatches` and a byte-identical
  `schemas/` vs `contracts/json-schema/v1/` drift check.
- A boolean-is-not-an-integer rejection, an invalid-RFC-3339-date-time
  rejection (proving `ajv-formats` is really enforcing `format`), and an
  `additionalProperties: false` rejection for `ProjectManifest` (the one
  contract that does not allow extension fields).

The two test files use the `.mts` extension (real ESM) purely so they can
use `import` syntax while `package.json` keeps `"type": "commonjs"` for
published output - `dist/` stays plain CommonJS (`require()`-compatible)
either way. `npm test`'s `pretest` step compiles them with a second,
test-only `tsconfig.test.json` (`rootDir: tests`, `outDir: dist-tests`,
not published - see `.gitignore`) before `node --test` ever runs, rather
than executing `.mts` source directly: Node's own unflagged TypeScript
type-stripping only exists from v22.18/v23.6 onward, so running the
`.mts` sources directly (as an earlier version of this client did) passed
locally on a newer Node but broke this repository's own CI, which pins
Node 20 (`.github/workflows/ci.yml`) to match `package.json`'s declared
`"engines": {"node": ">=20"}`. Compiling first keeps the test run
portable to any Node `>=20` with no dependency on that newer runtime
feature.

## Usage

```ts
import { validate, ContractValidationError, type HealthReport } from "@hydra-umc/sdk";

const report: HealthReport = {
  schema_version: "1.0",
  state: "READY",
  timestamp_utc: "2026-01-01T00:00:00Z",
  checks: { storage: { state: "PASS" } },
};

try {
  validate("HealthReport", report);
  console.log("valid HealthReport");
} catch (error) {
  if (error instanceof ContractValidationError) {
    console.error(error.message);
  }
}
```
